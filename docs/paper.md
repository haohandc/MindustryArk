# 用自建启动器在鸿蒙上运行未经改动的 JVM 游戏

**MindustryArk 项目技术报告**

---

## 摘要

鸿蒙（HarmonyOS NEXT）不再兼容 Android 应用，也没有可用的 Java 运行时。本项目要把
一款用 Java 写成的桌面游戏 —— Mindustry —— 原样运行在鸿蒙平板上，不修改游戏的任何字节码。

做法是自建一个**启动器**：它是一个正常的鸿蒙原生应用，在内部加载一份自己移植的 OpenJDK 21、
用 SDL3 提供图形与输入、并把游戏自己的 `.jar` 交给这份 JVM 执行。启动器与游戏是**两个可独立
更新的部分** —— 换游戏版本不需要重新构建启动器。

本文记录这套方案的构成、三个必须解决的核心障碍（ARM SVE 上的 JIT、匿名可执行内存、
Android 依赖的替代），以及本项目的证据方法：**凡是能测的就不推断**。

---

## 1. 问题

### 1.1 目标与约束

| 项 | 内容 |
|---|---|
| 目标软件 | Mindustry，桌面版，v8 Build 160.4 |
| 形态 | 单一 `.jar`，字节码 major 61（Java 17） |
| 目标平台 | HarmonyOS NEXT，平板 MatePad Pro，API 26，aarch64 |
| **硬约束** | **不修改游戏字节码** |
| 交付物 | 一个可安装的 `.hap`，上架应用市场 |

「不修改字节码」是本项目最关键的一条约束，它决定了后面所有设计：既然不能改游戏，
那么**所有平台适配都必须发生在游戏之外** —— 要么在 JVM 层，要么在 native 层，
要么在应用框架层。

### 1.2 为什么这不是「移植」

一个常见的误解是把这件事类比成「把 PC 游戏移植到手机」。实际上二者的困难完全不同：

- 常规移植的困难在**图形 API、输入模型、性能预算**；
- 本项目的困难在**运行时本身不存在**，且**宿主平台明确不允许某些运行时机制**。

Mindustry 用 Java 写，Java 需要一个 JVM；鸿蒙没有 JVM；所以第一个问题不是「怎么让它跑得快」，
而是「怎么让一个 JVM 在这里存在」。

---

## 2. 相关工作

Android 平台上的同类工作可以分成两条路线。**Boardwalk** 用一个 Java 层实现承载游戏逻辑，
**AMCL（Android Minecraft Launcher）** 则直接在 Android 上跑完整的 HotSpot。

本项目走的是后一条路线的思路，但目标平台不同、约束也不同：AMCL 的宿主是 Android，
Linux 内核语义完整，JIT 所需的内存权限天然可得；本项目的宿主是鸿蒙，
它**刻意收紧了可执行内存**（见 §4.2）。这个差别是本质性的 ——
AMCL 的许多适配手段（musl、信号处理、环境变量）本项目同样需要，
但它遇到的**核心障碍在本项目里根本不存在，而本项目遇到的障碍它也没有**。

因此本项目对 AMCL 取其思路，而不取其结论。

## 3. 系统架构

### 3.1 分层

```
┌──────────────────────────────────────────────┐
│  ArkTS 层   启动器界面（游戏列表 / 存档 / 设置）  │   正常鸿蒙应用
├──────────────────────────────────────────────┤
│  native 层  SDL3 + launcher.c（进程主控）      │   C，随应用编译
├──────────────────────────────────────────────┤
│  JVM 层     自编译 OpenJDK 21 (libjvm_real.so) │   未修改的 HotSpot
├──────────────────────────────────────────────┤
│  游戏层     mindustry-1.0.jar                 │   逐字节未改动的游戏
└──────────────────────────────────────────────┘
```

### 3.2 两条「游戏从哪来」的路径

启动器有一个开关 `SHIPS_GAME`，它决定包内是否携带游戏本体：

| | **完整版（master）** | **精简版（lite）** |
|---|---|---|
| 包内含游戏 | 是 | 否 |
| 首次启动 | 直接可玩 | 玩家自备 `.jar` 导入 |
| 用途 | 应用市场分发 | 玩家已有正版时使用 |

两版的 **ArkTS 与 native 源码逐字节相同**，差异只在一个常量与包内资源。
这样做的理由是：如果两版各维护一份源码，平台适配的修复就会分叉，
而平台适配恰恰是本项目工作量最大的部分。

### 3.3 启动链

```
EntryAbility.ets
  └─ import sdl from 'libSDL3.so'          ← SDL3 在这里加载
     └─ windowStage.loadContent('pages/Index')
        └─ Index.ets 创建 XComponent       ← Surface 在这里创建
           └─ libmain.so 被 dlopen         ← ⚠️ 只在这里加载
              └─ main() → start_jvm()
                 └─ JNI_CreateJavaVM
                    └─ 游戏 main() 进入 SDL 事件循环
```

其中标注 ⚠️ 的一步是排查期间的关键发现：`libmain.so`（启动器 C 代码所在的库）
**不在应用启动时加载，而在 XComponent 创建时加载**。这带来一个有用的推论 ——
不创建 XComponent 就等于不启动 JVM，这后来成了处理「无法运行」情形的手段。

## 4. 三个核心障碍

### 4.1 障碍一：ARM SVE 上的 JIT 崩溃

**现象。** JVM 建成后，游戏在执行到 JIT 编译的代码时崩溃。

**排查。** 崩溃点在 JIT 生成的代码里，而同样的 JVM 在 x86 上正常。
考虑到目标设备是 aarch64，怀疑点集中在 **SVE（可伸缩向量扩展）** ——
HotSpot 会为 SVE 生成向量化的代码，而本设备/本工具链对 SVE 的支持并不完整。

**解药。** 关闭 SVE：

```
-XX:+UnlockDiagnosticVMOptions -XX:UseSVE=0
```

**说明。** 这不是「关闭一项优化」，而是**让 JIT 不生成当前设备无法执行的指令**。
代价是失去 SVE 带来的向量化加速；收益是游戏能跑。对一个刚起步的移植来说，
这个交换是划算的 —— 而且它是可逆的：等工具链成熟后再打开即可。

### 4.2 障碍二：匿名可执行内存

**这是本项目最核心、也最昂贵的一个障碍。**

现代 JVM 的 JIT 需要一块**既可写又可执行**的内存：编译器把机器码写进去，然后跳过去执行。
这是 JIT 的定义所要求的，无法回避。（甚至解释执行也需要 —— 本项目实测确认。）

**鸿蒙在此处收紧了策略。** 实测得到的边界：

| 操作 | 结果 | errno |
|---|---|---|
| 匿名 `mmap(RW)` | 允许 | — |
| 匿名 `mmap(RWX)` | **禁止** | 22 EINVAL |
| 匿名 `mmap(RW)` → `mprotect(→EXEC)` | **禁止** | 22 EINVAL |
| 文件映射 `mmap(EXEC)` | **禁止** | 13 EACCES |
| `memfd` 后 `EXEC` | **禁止** | 13 EACCES |
| `dlopen` 系统库 | 允许 | — |

**关键读法：** 拒绝发生在**内核的 `mprotect` / `mmap` 这一层**，
因此**任何 JVM 参数都救不了** —— 不是 HotSpot 的问题，是内核不给。
唯一允许的可执行代码路径是**经签名的动态库**（`dlopen`）—— 那正是系统库能做的事。

**处置。** 鸿蒙为这类应用提供了一条**权限申请通道**：
声明 `ohos.permission.kernel.ALLOW_WRITABLE_CODE_MEMORY`。
本项目已提交申请并获批。获批后 JIT 正常工作。

**一个必须记录的坑。** 这个权限的生效取决于**签名**，而签名由**产品（product）**决定，
不由**构建模式（buildMode）**决定。实测教训：选「default 产品 + temp 构建模式」会得到

```
install failed due to grant request permissions failed.
PermissionName: ohos.permission.kernel.ALLOW_WRITABLE_CODE_MEMORY
```

因为 `buildMode` 只影响优化 / strip / 混淆，**产品才决定签名**。
见到这个报错，应当先查产品与签名，而不是怀疑权限申请本身。

**另一个必须记录的坑：判据只能是探针，不能是「系统在不在坚盾模式」。**

鸿蒙有一个「坚盾守护模式」，它关闭的正是可执行内存。于是很自然地会想用它的官方 API
判断能否启动。**这个想法被实测否定了。** 四份日志、两败两成、逐行对齐，
唯一差异在一行探针上：

| | 探针结果 | `create()` 之后 |
|---|---|---|
| 失败 #1 | `-1` | 19 行 `opt:` ⇒ **EOF** |
| 失败 #2 | `-1` | 同上 |
| 成功 #1 | `42` | `returned 0` + `JVM CREATED` |
| 成功 #2 | `42` | 同上 |

**且实测确认：坚盾模式关闭时，也出现过探针失败。**

这里有一条可以推广的判据：

> 一个指标如果**直接量到结果**（能不能拿到内存），它天然覆盖全部成因；
> 一个指标如果**只描述一种状态**（在不在某模式），它只覆盖那一种。

后者的诱惑力恰恰来自它「更权威」—— 官方 API、有文档、有版本号。
但**权威 ≠ 相关**。本项目为此多花了好几轮排查。

### 4.3 障碍三：Android 依赖

游戏虽用 Java 写，但它并非纯 Java —— 它依赖一些在桌面/Android 上常见的设施，
而在鸿蒙上这些**不存在**。

| 依赖 | 状况 | 处置 |
|---|---|---|
| 图形 / 输入 / 音频 | 依赖 LWJGL（绑定桌面 GLFW） | 换成 **SDL3**；游戏侧通过 `-Darc.sdl.dispatchFix=` 走 SDL 分发表 |
| 文件对话框 | `libarc-filedialogsarm64.so` 基于 tinyfiledialogs，**glibc 链接** | 本平台无法加载；游戏的「导入模组」按钮**永不工作**，由启动器提供替代入口 |
| 网络 | ArcNet 全 NIO | NIO 在内核上可用；加 `INTERNET` 声明后实测打通 |
| 文件系统外部路径 | `OS.userHome` 派生 | 用 `-Duser.home` 指向沙箱，**已生效，不要动它**（改它等于搬走玩家存档） |

## 5. 启动器的形态

### 5.1 为什么要做成启动器，而不是打包成一个整体

这是本项目最重要的一个设计决定。

把游戏和运行时装进一个不可分的产物，在早期调试阶段是方便的。但它有两个难以承受的代价：

1. **换游戏版本 = 重新构建整个应用**，而每次构建都要重新走一遍平台适配的验证；
2. **两版分发（完整版 / 精简版）会分叉源码**，而平台适配的修复必须同时落到两处。

做成启动器之后：JVM 与平台适配是**应用的一部分**，游戏是**一个数据文件**。
换游戏版本只需导入一个新的 `.jar`，不触碰任何平台代码。

### 5.2 玩家可见的能力

- **多版本并存**：不同版本的游戏 jar 各自隔离数据目录，存档互不干扰；
- **存档管理**：按存档 / 按版本两个视图，复制、移动、删除；
- **模组导入**：把 `.jar`/`.zip` 放进游戏的 `mods/` 目录（游戏启动时自动扫描）；
- **异形屏避让**：挖孔 / 刘海区域自动避让，并保留手动滑条覆盖。

### 5.3 一个主动的放弃

鸿蒙的窗口默认带系统栏。本项目在游戏运行时隐藏它们（沉浸模式），
这样游戏画面能铺满屏幕 —— 这是游戏该有的样子。代价是玩家失去系统返回键，
因此启动器自己提供了一个页内返回键。

## 6. 证据方法

本项目的技术结论如果不标注证据强度，就会在几次压缩之后退化成「我记得是这样」。
因此本项目采用一套固定的标注：

| 标记 | 含义 |
|---|---|
| ✅ | 已核实 —— 有源码、官方文档或设备实测支撑 |
| 🔶 | 推断 —— 合理但未验证 |
| ❓ | 待查 |
| ⛔ | 已推翻 —— 明确记录「别再这么说」 |

并且记录结论时用四段式：**结论 + 依据 + 置信度 + 影响面**。

### 6.1 本项目付出代价最多的两类错误

**第一类：用「更权威的间接指标」替换「直接量到结果的指标」。**
见 §4.2 末。一个官方 API 看起来比一个自制探针可信得多，
但它回答的是**另一个问题**。换掉之后，覆盖全部成因的指标被换成只覆盖一种成因的指标。

**第二类：能测的东西去推，能读的日志去猜。**
本项目有一次连续给出三个「从源码推出」的根因，**全错**；
而正确答案**一直躺在早就拿到的那份日志里**。
此后的判据是：

> 推理一个运行时行为之前，先问「有没有一条命令能直接看到它」。
> 有 ⇒ 去要，别推。

### 6.2 测量方法论中确实踩过的坑

以下每一条都是真金白银换来的，且都**不是「注意一点」就能避免的** ——
它们的共同点是**错误的结果看起来完全正常**：

- **环形缓冲区里的「空结果」是关于缓冲区的陈述，不是关于写入方的。** 日志里 grep 不到，
  第一反应是「应用没写」，实际是缓冲区已经转过去了。
- **测量工具自己会截断，而截断看起来像「结果就是这么多」。** 穷举测试期望 364 条诊断，
  实际跑出 38 条 —— 因为编译器的 `-ferror-limit` 默认在 20 处停下。
- **「每次启动都报 PASS」的检查等于没有检查。** 闸门要建在**产物**上，
  而且要断言「它确实检查了这一次的东西」。
- **产物是从工作区构建的，所以它证明不了版本控制里有什么。** 发版前必须**另行核对**。
- **一条写死的「平台限制」，可能只在它被写下时的工具链状态下成立。**
  本项目源码里长期写着「C 文件必须纯 ASCII，否则中文注释会提前结束注释块」，
  且带有「违反过四次」的实例。等到实测时才发现：**182 个非 ASCII 字符全部正常闭合，
  零问题，构建通过**。一条被写进源码、抄进笔记、还带着历史案例的规则，
  **全都不构成它现在仍然成立的证据**。
- **记下一条教训不等于不会再犯 —— 除非操作本身被改掉。**
  本项目有一个命令误用被当场查明、当场写进提交信息、当场告知，
  **几十分钟后又踩了同一个**。凡是「靠记得」才能避免的错误，都会再犯；
  修法是把正确做法变成**命令的形状**，而不是变成一条知识。

## 7. 结论

### 7.1 结果

- 游戏在鸿蒙平板上**完整运行**，帧率与交互正常；
- 应用已提交华为应用市场（`1.0.0.2`，首个带权限、可上架的版本）；
- 启动器支持多版本游戏 jar 与存档隔离；
- 一份精简版（不含游戏本体）供已有正版的玩家使用。

### 7.2 这套方案的可迁移性

本方案**不依赖 Mindustry 的任何特性**。它适用的条件是：

1. 目标是一个用 JVM 语言写成的程序；
2. 能拿到一份可编译的 HotSpot（本项目用的是 OpenJDK 21）；
3. 程序的图形 / 输入 / 音频依赖可以被替换（本项目用 SDL3）；
4. 宿主平台**允许**某条路径拿到可执行内存 —— 无论是有权限、有豁免，还是签名例外。

第 4 条是唯一的硬门槛：**如果宿主平台在架构上完全禁止可执行内存，
且不提供任何申请通道，那么这条路走不通。** 本项目之所以成立，
是因为鸿蒙在收紧了默认策略的同时，**保留了一条可申请的通道**。

### 7.3 一句话

**「能不能跑起来」从来不取决于开发者有多想让它跑，而取决于宿主平台留没留那条缝。
找到那条缝、证明它就是那条缝、然后从那里过去 —— 这就是全部工作。**
