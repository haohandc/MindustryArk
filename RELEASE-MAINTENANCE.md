# Release maintenance

**Maintainer and audit record. Users want `RELEASE.md` instead.**

Everything here is either evidence, rationale, or a past incident. None of it is needed
to download or install the app, which is why it does not live in the release notes.

---

## 1. What may be published, and what must not

| Artifact | Publish? | Why |
|---|---|---|
| `MindustryArk-v<version>-unsigned.hap` | **yes** | Anyone can sign it with their own certificate and install it. This is the app. |
| `MindustryArk-v<version>-payload.zip` | yes | Build inputs. Not needed to play. |
| `MindustryArk-v<version>.hap` (signed) | **NO** | Device-locked, and it discloses personal data. |

### Why the signed HAP is never a release artifact

`deploy.sh` builds one because the local development loop needs one. It is signed with a
**debug** profile generated by DevEco Studio, and that makes it unfit to hand to anyone
for two independent reasons — either one alone is disqualifying.

**1. It only installs on devices whose UDID is in the profile.**

A debug profile is a list of permitted devices. Huawei's own documentation for requesting
one: "*Click **Select** and select one or more debugging devices. You can select up to 100
devices.*" (<https://developer.huawei.com/consumer/en/doc/agc-help-debug-profile-0000002248181278>),
and for registering them, "*you need to register the device with the AppGallery Connect
device list using the UDID*"
(<https://developer.huawei.com/consumer/en/doc/agc-help-add-device-0000001946142249>).

The restriction lives in the **profile**, not the certificate: a Release profile has no
device list at all ("*a list of devices permitted for debugging (empty for Release type
apps)*", <https://dev.to/harmonyos/how-to-solve-the-manual-signature-issue-41lj>). A
third-party distribution service says the same from the other side — a debug certificate
is refused outright, and the profile must be Specified Device Release *with the tester's
UDID in it* (<https://www.pgyer.com/doc/en/view/harmonyos>). Its error 10021 is literally
"the device UDID isn't in the profile's scope".

**2. It contains the UDIDs and the developer's real name, in the clear.**

This is worse, because it is not an install failure — it is a disclosure. **Measured, not
assumed.** The profile sits in the signing block as plain JSON:

```bash
python - <<'PY'
p = "entry/build/default/outputs/default/MindustryArk-v0.2.0-beta.1.hap"
d = open(p, "rb").read()[-400000:]
i = d.find(b'"debug-info"')
print(d[max(0, i - 900):i + 400].decode("utf-8", "replace"))
PY
```

which prints

```
"type":"debug",
"bundle-info":{"developer-id":"…","development-certificate":"…CN=…,Development…"},
"debug-info":{"device-ids":["…","…","…","…","…","…"],"device-id-type":"udid"}
```

Six UDIDs, the developer account id, and the name on the certificate. Hardware
identifiers tied to an account. Uploading them is **not recoverable** by deleting the
release afterwards — assume anything uploaded is cached.

> **Conclusion: build the signed HAP locally, install it locally, never upload it.**

**A cheap check that works.** The four markers above plus a 64-hex count, run against the
candidate **and** the signed build. The signed one must light up, or the check proves
nothing:

```bash
python - <<'PY'
import re, os
for fn in ["…-unsigned.hap", "….hap"]:
    d = open(fn, "rb").read()[-900000:]
    hit = [m.decode() for m in [b'debug-info', b'device-ids', b'developer-id',
                                b'development-certificate'] if m in d]
    print("%-46s markers %d/4  hex64 %d" % (os.path.basename(fn), len(hit),
          len(set(re.findall(rb'\b[0-9a-fA-F]{64}\b', d)))))
PY
```

### If a pre-signed build is ever genuinely wanted

It needs a **release certificate** and a Release profile from AppGallery Connect, which
needs a real-name-verified developer account. Two caveats before promising it to anyone:

- A Release profile has no device list, which is what would make the result installable on
  arbitrary devices. Read from the profile format (source above); **not tested here**.
- Full distribution through AppGallery also means app review, which an unofficial
  Mindustry launcher would not pass on licensing grounds. See `THIRD-PARTY.md`: a build
  redistributes GPL-3.0 Mindustry, so it can only be distributed with its source, which is
  what this repository is for.

version rename, and the size moved by 3,760 B (272,557,304 → 272,561,064) with identical
content — `verify_hap.py` passes on both and every payload sha1 matches. Zip timestamps
and entry order are not stable, so **bytes are not reproducible; content is.** Record the
hash of the file that is actually uploaded, not the first one built.

### 2.1 Why a ledger is needed — two independent reasons

**GPLv3 §6.** Distributing a binary carries the Corresponding Source obligation, and the
repository moves on: `master` stops being the Corresponding Source for an older binary the
moment anything lands. A tag per release is what makes "which source belongs to this
binary" checkable.

> Stated precisely, because a rule asserted more strongly than it really is stops being
> persuasive: §6 requires the source to be **available**, not that a tag exist. But
> without a tag the correspondence cannot be *shown*, and an unshowable correspondence is
> not a discharged obligation.

The part that actually matters here: we ship a **modified** Mindustry, so the modifications
have to be available. This repository carries them as the patch scripts
(`build_arc_patch.py` → `patch_mindustry.py` → `build_variants.py`) plus an exact
identification of the upstream version — the established distribution practice. It only
holds while the upstream version is pinned, which is why the game jar's **sha1** is
recorded and not just its version number.

**The versionCode is derived, and its ordering is not readable from the name.**

```
base = major*1000000 + minor*10000 + patch*100          pre-release +1..98, final +99
```

| versionName | versionCode | |
|---|---|---|
| `0.1.0-beta1` | **10001** | |
| `0.1.0-beta2` | 10002 | |
| `0.1.0` (final) | **10099** | ⚠️ sorts BELOW the next line |
| `0.1.1-beta1` | **10101** | ⚠️ sorts ABOVE the previous line |
| `0.2.0-beta.1` | **20001** | |
| `1.0.0` | **1000099** | |

⇒ The relative order of `0.1.0` and `0.1.1-beta1` is **not** visible in the names. The
authority for the rule is `scripts/config.py`; this table is a readable copy, and every
number in it was checked against `version_code_for()` after being written.

### 2.2 The published 10001: one version, two spellings

That build predates the move to a dotted pre-release, so the same version is written two
ways in three places:

| Where | Says |
|---|---|
| Git tag / file names / release title | `v0.1.0-beta.1` (**dotted**, renamed after the fact) |
| ⚠️ **Inside the package**, `versionName` | **`0.1.0-beta1`** (**undotted**, written at build time) |

⚠️ **Cannot be corrected** — re-uploading would change the bytes and invalidate the
recorded sha256. **And is not worth correcting:** the platform decides upgrade eligibility
from **`versionCode` (10001, unchanged)**, not from the spelling. ⭐ **So do not republish
this version to make the three agree.** If someone reports the mismatch, this table is the
answer. From `0.2.0-beta.1` onward the three agree by construction.

### 2.3 A tag that pointed at the wrong commit (2026-09-21, fixed)

Renaming the tag from `v0.1.0-beta1` to `v0.1.0-beta.1`, **GitHub resolved the new tag to
the default branch as it stood** — `bba382e`, eleven commits *after* the commit that
produced the binary. The release page's auto-generated source archives briefly offered
source that could not have built the asset beside them, which is exactly the mismatch this
ledger exists to prevent.

Fix, and **do not use the release editor to do it** — re-entering the tag name there is the
one action that reproduces the fault:

```bash
git push origin :refs/tags/v0.1.0-beta.1          # delete the wrong one
git push origin 332192e:refs/tags/v0.1.0-beta.1   # recreate at the right commit
git ls-remote --tags origin                        # verify
```

Verified after: the tag points at `332192e`, and the release id (`392362924`), title,
pre-release flag and both assets — **including their sizes** — were unchanged.
⭐ So **deleting a tag does not delete its release**, and recreating the tag under the same
name re-links them on its own.

⚠️ **Lesson: when renaming a tag on GitHub, the target must be pinned to a commit.** The
default it offers is a **branch**, and a branch moves — the default is precisely the wrong
answer here. Same shape as this repository's rule about identifiers: read them, do not
reconstruct them.

⚠️ Two tags now point at the same commit (`v0.1.0-beta.1` and the leftover `v0.1.0-beta1`).
Both are correct, nothing depends on removing the old one, and it is the only remaining
record that the release was ever published under the undotted name.

### 2.4 That tag had already been moved once before, deliberately

The reference-launcher's artifact paths were rewritten out of history (the repository's git
log says why), which changed **every commit SHA**. So `v0.1.0-beta1` was re-pointed from
`fd6e021` to `332192e` and force-pushed.

⭐ **The tag's tree is byte-identical** — `59a49bf02784418e226d4cf4b11f6cfa6b93a166`. So the
source archives GitHub generates for it are unchanged; only the commit SHA in the page
header moved. Worth keeping on record, because "the tag moved" reads alarming and in this
case it is not.

## 3. Release page copy

### Title

```
v0.2.0-beta.1 — Mindustry v8 Build 160.4 (unofficial HarmonyOS port)
```

### Body

Pasted from **`dist/RELEASE-BODY-v<version>.md`**.

⚠️ **That file is not a copy of `RELEASE.md`** — the two have different jobs:

| File | Covers |
|---|---|
| `RELEASE.md` | The standing notes: what the files are, how to install, verified devices, known limitations. **Version-independent**, and **keeps its H1** because it is read in the repository |
| `dist/RELEASE-BODY-v<version>.md` | The release page copy. Differs from `RELEASE.md` in exactly three ways, below |

**The release page is an announcement. `RELEASE.md` is the manual.** A release body that
also carries install steps, limitations and build instructions buries the one thing a
reader came for — what changed — under material they can find at leisure.

**What the body keeps** (three sections, and that is all):

| Section | Why it stays |
|---|---|
| What is new | The reason the page exists |
| Which file to download | Two files, and nothing says which is which |
| Verified | Short, and it is the only evidence that it runs at all |

**What the body drops** — H1, the opening description, installing, known limitations,
building from source, credits — with **one pointer line** to the README in its place.

⚠️ **The pointer line is not decoration.** The downloaded artifact is an *unsigned* HAP,
which **will not install**. Dropping the install steps without saying where they are
strands the reader at step one. One line solves that; the sections do not have to be here.

⚠️ **Two things must survive the trim, and they sit where the trim happens:**

- ⚠️ **The unofficial + GPL-3.0 notice.** It lives beside the opening description and was
  deleted along with it once already. It is the load-bearing statement about what this
  project is; keep it in **both** language halves.
- ⚠️ **The embedded game version** (`Mindustry v8 Build 160.4`). Our own version number says
  nothing about which upstream build is inside, and the body is where a downloader looks.

⇒ To produce a body: take the version sections, keep the notice, add "what is new", and end
with the pointer. The material that was dropped lives in `README.md` and `RELEASE.md` — do
not delete it from those to "avoid duplication"; they are the manual.

⚠️ **`Full Changelog` at the foot of the page is generated by GitHub** — leave it alone.
It compares the previous tag against the new one, so it is correct only while the previous
tag points at the commit that produced the previous binary. See 2.3.

## 4. Building the two artifacts

```bash
bash build.sh assembleHap                # -> the HAPs, in entry/build/.../outputs/default

# the payload zip, from the assembled payload. Rebuild it whenever entry/libs changes,
# or the published zip will disagree with the repository:
python - <<'PY'
import os, zipfile, sys
sys.path.insert(0, "scripts")
import config
with zipfile.ZipFile("dist/%s-payload.zip" % config.ARTIFACT_NAME, "w",
                     zipfile.ZIP_DEFLATED, compresslevel=9) as z:
    z.write("dist/README-PAYLOAD.txt", "README-PAYLOAD.txt")
    for dp, _d, fs in os.walk("entry/libs"):
        for f in sorted(fs):
            p = os.path.join(dp, f)
            z.write(p, p.replace(os.sep, "/"))
PY
```

The zip carries `entry/` at the top level and `README-PAYLOAD.txt` beside it, so unzipping
into the repository root does the right thing.

⚠️ **A version bump touches THREE files, and the third is easy to miss:**

| File | Field |
|---|---|
| `scripts/config.py` | `APP_VERSION` / `VERSION_CODE`, self-checked on import |
| `AppScope/app.json5` | `versionName` / `versionCode` — what the device reads |
| `entry/build-profile.json5` | `artifactName` — a **hand-written duplicate**, not derived |

Doing only the first two ships a package named after the previous version.
`verify_hap.py` has a gate for exactly that and will say so.

## 5. Pre-publication checklist

- [ ] `python scripts/verify_hap.py` → `RESULT: PASS`
- [ ] `python scripts/test_version_gate.py` → 7/7 (re-run whenever a version field moves)
- [ ] Signature-block check on the candidate **with the signed build as a control**
- [ ] Payload zip rebuilt if `entry/libs` changed
- [ ] sha256 recorded for the file that will actually be uploaded
- [ ] Repository has no local absolute paths. The leading boundary group is what keeps this
      from matching every `https://` in the docs:
      ```bash
      git grep -nE '(^|[^A-Za-z0-9])[A-Za-z]:[\/\\]' -- . ':!entry/src/main/cpp/SDL' ':!LICENSE' ':!RELEASE.md'
      ```
      A control for the pattern itself, in a quoted heredoc because `printf` eats the
      backslashes:
      ```bash
      cat <<'EOF' | grep -nE '(^|[^A-Za-z0-9])[A-Za-z]:[\/\\]'
      ok https://x.dev/a
      bad E:/u/x
      bad C:\Users\y
      EOF
      ```
      ⭐ This check has caught real defects twice, including a hard-coded absolute path in
      `scripts/test_version_gate.py` that would have failed with a confusing `ImportError`
      in any other checkout.
- [ ] **Signed HAP is not attached.**
- [ ] Tag target pinned to a commit, not the default branch.
